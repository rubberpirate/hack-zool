# HTTP API

The checked-in `openapi.json` is generated from Utoipa annotations. Run `cargo run -p zsplit-api -- --export-openapi` to regenerate it; development Swagger is at `/docs` only with `ENABLE_DOCS=true`.

Configure one organizer's UUID and an API token of at least 32 characters. The API compares a SHA-256 digest in constant time and checks room ownership in every SQL operation. This MVP has no enrollment, password login, or multiple organizer session management. Serve behind TLS. Never put organizer or claim bearer tokens in query strings; all query strings are rejected. Request tracing records only generated request ID, HTTP method, status and elapsed time.

Create a room using `POST /api/v1/rooms` with `Authorization: Bearer <organizer-token>` and JSON `{"network":"testnet","amounts_zat":[1000000,1000000],"expires_at":"<future RFC3339 timestamp>"}`. The room exposes its dedicated native coordinator account deposit address through the owner-only `/deposit` endpoint. Fund it externally and wait for native SDK synchronization. Issuance requires fresh confirmed spendable funds covering all payouts plus 100,000 zatoshis of reserved fee budget per ticket. This budget is conservative, not a quoted exact fee.

`POST /api/v1/rooms/{id}/claims` returns `tickets` once, including each `claim_id`, raw `token` and fragment-only `claim_url`. An interrupted issuance response cannot recover the raw tokens from the database. Do not retry room issuance expecting a second batch: it returns a conflict. Keep the initial response securely until ticket distribution is complete.

Claim metadata/status require `Authorization: Bearer <ticket-token>`. The browser creates and persists an ephemeral Orchard wallet, keeps all keys locally, and POSTs `{"ephemeral_receiver":"<Orchard-capable unified address>","idempotency_key":"<UUID>","client_network":"testnet","wallet_persisted":true}` to `/api/v1/claims/{claim_id}/redeem`. The persistence flag is a client attestation; the server cannot inspect browser key storage. Unknown JSON fields (including accidental key fields) are rejected. The server cannot distinguish an ephemeral receiver from a user's existing personal receiving address: compatible clients must enforce the privacy contract.

A winning redemption returns HTTP 202 with stable `claim_id`, `payout_id`, `status:"funding_queued"` and `poll_after_ms:2000`. Exact retries with the same operation key and receiver return the original operation even if the claim has progressed. Different receivers or keys conflict. Poll `/status` for current chain-sensitive status. HTTP 202 acknowledges a durable payout intent, not successful payment.

The owner-only SSE `/events` stream emits full `room_summary` snapshots every two seconds. Use authenticated `fetch()` streaming; browser EventSource cannot supply an Authorization header. The service caps concurrent streams at 32. No recipient receivers, raw tickets, or keys appear in summaries. `funded_confirmed_count` is authoritative; `sweep_reported_count` is a distinct unverified client report. Sweep reports are accepted only for a confirmed payout and never replace its funding state.

Owner withdrawals accept `organizer_receiver`, `amount_zat`, `network` and `idempotency_key`. The organizer receiver must be an Orchard-capable unified address on the configured network. Withdrawals reserve amount plus fees and use the same durable payout worker as claims. Internal withdrawal intents cannot be accessed through public claim endpoints.

JSON error responses contain `code`, `message` and a generated `request_id` matching `X-Request-Id`. Errors do not echo submitted data. Invalid tickets return a low-information 404. A room's balance must have been updated in the past 120 seconds with a scan lag of no more than two blocks for issuance/redemption/withdrawal. `/readyz` checks PostgreSQL, dispatcher liveness and those scan freshness conditions; a newly-created room can be briefly unready until its first sync.

The API limits bodies to 16 KiB, response latency to 30 seconds before headers, 240 requests/minute per direct peer IP and 500 requests/second globally. It deliberately does not trust X-Forwarded-For. Deployments behind a reverse proxy share the proxy peer limit until a trusted-proxy policy is implemented. CORS uses one explicit HTTPS origin (HTTP permitted only for localhost development). Financial confirmations always come from native wallet/chain state; there is no API for setting balances or marking payouts confirmed.
